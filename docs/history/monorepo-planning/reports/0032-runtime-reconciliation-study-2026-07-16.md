## Executive verdict

Both sides built a desktop plugin runtime on the **same unchanged contracts** — `packages/plugin-api` and `packages/plugin-host` have a zero diff base→main, and our extensions to them are additive and (verified) signature-compatible with every call main's code makes. Main's plugin layer is small (~770 lines, 11 tests, Phases 1–3 of its *toolbars* plan) but sits on two things we lack: a **stable shared CommandRegistry** (the Phase-1 refactor that obsoletes our A2/A3 workaround and makes our design *simpler* to port) and a **4,200-line new toolbar/palette subsystem** that plugin toolsets feed into; ours is deep (38 desktop files, ~198 plugin tests, worker isolation, installer, manager, menus, interactive linked figure) but wired to the base-era MainWindow. The collision is real in only four places — the runtime wrapper, command dispatch, panels, and MainWindow.tsx — everything else is cleanly additive on one side or the other. Recommended union: **main as the git trunk, ours as the plugin architecture**, porting main's four plugin-specific capabilities (registry integration, toolset contributions + rollback, disk storage, patch-review tray) onto our runtime, with panels kept in-app now (Option A) and the unified-renderer separate window (Option C) as a designed follow-up. The owner must decide (a) the panel model and (b) confirm ours-as-plugin-base; everything else in this report is executable as written.

### 1.1 Files in `origin/main:apps/desktop/src/plugins/` (715 lines total)

### 1.2 The command-registry refactor (the high-priority lead — CONFIRMED)

`caa182fc` created `origin/main:apps/desktop/src/commands/coreCommandRegistrar.ts` (55 lines; the directory did not exist at base and does not exist on ours — verified with `git ls-tree 64cf513e` and `ls`). The base problem is exactly our ledger's A2/A3 (STATUS.md rows 140–141: registry built in a MainWindow `useMemo` whose deps include selection, so it rebuilt on selection change — the reason our host lives in a ref). Main's fix, from the commit body: the 41-dep handler block now populates a **plain `Map` of core bindings** (rebuilt per render, cheap), while the `CommandRegistry` itself is created **exactly once** and kept in sync by pure `createCoreCommandRegistrar(registry, getLiveBindings)`: registered handlers delegate through the live-bindings ref (always the latest closure), the enabled-gate lives in the delegating handler (:41–51), and `sync(bindings)` registers added / unregisters removed ids while "plugin commands registered separately into the same registry are never wiped" (doc :10–20 — "Phase 2 relies on this"). Wiring on main: bindings ref at MainWindow :6661–6663 with the explanatory comment :6665–6668; one-time registry + registrar memo :7125–7134 (`useMemo(..., [])`); `syncCoreCommands(coreCommandBindings)` effect :7136–7138. Core bindings deliberately **skip `tool.source === "plugin"`** so a core binding never collides with a host-owned plugin command or strips its permission checks (:6891–6903). Scope note in the commit: the cosmetic extraction of handler families into `commands/*.ts` files was deferred — the 23.7k-line MainWindow stays.

**What this means for us:** the constraint that shaped `createPluginRuntime`/`usePluginRuntime` (host in a lazy ref because the registry churns — A2/A3) is gone on main. Our host can now simply **share the stable registry**: `PluginHostOptions.commandRegistry` is still an optional injection point on our extended host (`packages/plugin-host/src/index.ts:150`, constructor :185 `options.commandRegistry ?? new CommandRegistry()`), and our `host.invokeCommand` already has main's exact single-dispatch semantics — no `pluginId` on the definition ⇒ plain registry dispatch; `pluginId` present ⇒ dispatch with the plugin's permission context (`packages/plugin-host/src/index.ts:240–255`). The port is a *simplification*: keep `usePluginRuntime` unchanged, add an optional `commandRegistry` passthrough to `createPluginRuntime`'s options, and MainWindow's dispatch can collapse to main's single `host.invokeCommand` fallthrough (origin/main:MainWindow.tsx:7281–7286) wrapped in our ADR-0010 `{ ok:false }` surfacing (`pluginCommandFailure`, usePluginRuntime.ts:25–31). One semantic to guard: our `isPluginCommand` is currently `host.commands.has(id)` (usePluginRuntime.ts:175) — correct only while the host's registry contains *only* plugin commands. Under a shared registry it must become a `pluginId`-ownership check (`host.commands.get(id)?.pluginId !== undefined`) or disappear entirely in favor of single-dispatch.

### 1.5 Panel mechanism (verified: a separate native window)

Routing: `origin/main:apps/desktop/src/App.tsx:38–41` — if `pluginPanelRouteId()` finds `?window=pluginPanel&panelId=…` (:46–57) the app renders `<PluginPanelWindow panelId=…/>` instead of MainWindow. Window creation: Rust `open_plugin_panel_window` (origin/main:apps/desktop/src-tauri/src/lib.rs, command listed :398, body ~:829–867): validates the panel id with the same charset guard as storage ids, labels the window `plugin-panel-<panelId>` (dots→dashes), reuses+shows an existing one, else builds a `WebviewWindowBuilder` at `/?window=pluginPanel&panelId=…`, default 380×520 (min 280×200), `decorations(false)`, `skip_taskbar(true)`, then `configure_toolset_utility_window(&window, true)` — the doc comment: "Plugin panel windows get the same floating-utility treatment as toolset palettes: they float above the document while the app is active and hide with it on deactivate." A declarative `PluginPanelReport` reaches it as data over the request/broadcast bus (§1.1 panelBridge); the window holds **no plugin code**. Because windows are keyed per `panelId` and the main window keeps a `Map<panelId, payload>` (:7141), **main supports multiple panels open concurrently** — ours is deliberately one-panel-at-a-time (§2). Capabilities: the `plugin-panel-*` window glob plus `core:window:allow-hide` were added in the Phase-3 capability change (diff shown in §4, file 5). *(Runtime float/hide behavior is inferred from the code and commit message; the app was not executed.)*

## 6. Behavioral deltas that matter for a union

1. **Rollback semantics.** Main: a bad toolset contribution unregisters the *whole* plugin (`pluginRuntime.ts:67–70`; pinned by test 3). Ours has no toolset stage, and host-level `registerPlugin` validation throws atomically before commit (base behavior). Union must preserve main's rollback when the toolset stage is ported into our runtime — port the try/catch with the provenance maps.
2. **`requirePermission`.** A base host API (plugin-host is unchanged on main). Main's desktop calls it for `ui.toolbar` (:57); our desktop never calls it directly — permission gating on ours happens via context construction (`plugin-host/src/index.ts:325–355`) and worker-bridge namespace checks. No conflict; the ported toolset stage brings main's one call site with it.
3. **Can our M32 manager disable a plugin that contributed toolsets?** Yes, mechanically: ADR-0027 disable = `unregisterPlugin`; main's `unregisterPlugin` clears the provenance maps and fires `onDidChange` (:74–79) → MainWindow effect re-runs `setPluginToolsets` (:7182–7183) → catalog rebuild removes the palette. Verified as a code chain; not executed.
4. **Fixture vs bundled catalog.** Id-disjoint; fixture is DEV-only. Post-union, in dev builds the fixture would appear in our manager's plugin list (it enumerates `host.listPlugins()`); cosmetic — decide to filter or show.
5. **Selection payloads.** Main's provider sends unfrozen `{objectId, structureFormat, structure}`; ours adds document/page identity + `sourceFingerprint` and the host freezes snapshots. Ours is a strict superset and type-compatible (§2). Union: replace main's inline provider with `buildPluginSelectionSnapshot` — main's runtime test 5 still passes (it fakes its own provider).
6. **Panels: one-at-a-time vs many.** Ours enforces a single open panel with real close notification on replacement (`PluginPanelController.ts:36–43`, ADR-0012 cancellation); main opens one *window per panelId* with revision-guarded rebroadcast. A union on Option A keeps single-panel semantics; B/C make multi-panel possible and must decide whether replacement-close semantics still apply per surface.
7. **Staleness + Run again.** Ours: report `source` fingerprint vs live document (MainWindow :1830–1834) + `onRunAgain` via `rerunCommandId`. Main: neither (a stale report just sits there). Union keeps ours; in a separate window both need a small bridge (§7).
8. **Main's test pins vs our design.** Nothing main pins contradicts our architecture: its six runtime tests pin the toolset stage + shared-registry routing (both of which we adopt), catalog pruning (toolbars feature), and context selection/panel wiring (shared base behavior our host still satisfies — its `getSelection` returns our frozen superset snapshot, and `sections:[{kind:"text",…}]` still validates). `origin/main:App.test.ts:157–165, 256–264` registers the fixture through the runtime and asserts the composed registry — survives as long as the union runtime keeps a `registerPlugin`+toolsets path and the test's import is updated.
9. **Storage.** Main's disk-backed storage changes plugin-visible behavior (persistence across restarts) — pure upgrade; our NMR/mass-fragment plugins currently rely only on in-memory semantics, and the interface is identical.

## 7. THE PANEL QUESTION — framed for the owner

**Ground truth established by reading code:** (i) Both sides consume the same validated `PluginPanelReport`. (ii) Our `PluginReportRenderer` is a pure function of the report (`PluginReportRenderer.tsx:11`) — it can render anywhere React runs, including main's panel window. (iii) **The interactive linked figure does NOT touch the main canvas**: `LinkedFigureView` receives `spectrum` + `structure` as plugin-shipped data inside the `linkedFigure` section (`LinkedFigureView.tsx:28–37`; ADR-0015 comment in plugin-api diff), and the hover cross-highlight is an internal peak↔atom mapping (`:99–109`). The presumption that "hover linkage to the main canvas breaks in a separate window" is **false** — there is no canvas linkage to break. (iv) Main's `PluginPanelWindow` renders only text/keyValue/table/svg and **silently drops unknown kinds** (`origin/main:…/PluginPanelWindow.tsx:139–140`) — so Option B *without* porting our renderer silently loses the entire NMR figure. (v) What genuinely doesn't carry into a separate window today: the **Run again** button (needs an invoke path back to the main window — one more panelBridge message), the **stale badge** (main window computes it against the live document; needs a push), and our expand-modal (superseded by native window resize). Clipboard copy / JCAMP export should work in panel windows under merged capabilities (the `plugin-panel-*` window glob is in main's capability list and our `fs:` additions are window-scoped the same way) — *inferred from capability config, not executed*.

- **Option A — in-app (ours), port cost ≈ 0.** Keeps everything shipped and tested (14 surface tests + 25 LinkedFigureView tests): drag, expand modal, stale badge, run-again, exports. Loses: floating above the document while other windows focus; multi-panel. Main's panelBridge/PluginPanelWindow/Rust command remain unused (keep dormant or delete).
- **Option B — separate window (main's), port cost = moderate, plus regressions.** Native float/hide-on-deactivate matches main's palette paradigm; multi-panel. Requires porting `PluginReportRenderer` into `PluginPanelWindow` anyway (or NMR loses its figure), plus a rerun/staleness bridge; deletes our surface (and its drag/expand/stale UX) and repoints 14 dom tests.
- **Option C — both, unified renderer.** `PluginPanelWindow` swaps its `PanelSection` switch for our `PluginReportRenderer` (small: the window becomes chrome around the same renderer); panelBridge carries `{report, revision}` as today plus two new messages (`invoke rerunCommandId`, `staleness`); the in-app surface stays for the default/browser build, and "open as window" becomes panel chrome. Cost: the bridge messages, capability check, and a policy for single-vs-multi panel; benefit: one renderer, both UXes, no dead code.

**Recommendation:** **A now, C as the designed follow-up.** A is free and regression-less at merge time; C is cheap *after* the union because the renderer is already pure and the bridge already exists — do it when the owner wants panels to float like main's palettes. B alone is strictly dominated by C.
